# 规则工程化 · 元规则框架

> 一套"如何设计与维护 AI 协作规则"的通用方法。不绑定任何具体组织/人设，可直接套用。

## 一、规则三层结构

| 层 | 范围 | 例子 | 维护频率 |
|----|------|------|---------|
| L0 宪法 | 全部 Agent 必守 | 真实为本 / 不泄密 / 去 AI 味 | 极少变更 |
| L1 标准规则 | 全局场景 | 发布门禁 / 质量门禁 / 引用规范 | 按需修订 |
| L2 按需规则 | 局部 / 临时 | 单个项目 / 单类任务 | 高频迭代 |

分层原则：**L0 宁少勿多**（都是红线）；能放 L2 就不放 L1（避免全局噪音）。

## 二、规则编码规范（RFC 风格）

```
<域>-<序号>：规则标题
```
- 域前缀：SAF（安全）/ BUL（信任与依据）/ PUB（发布）/ QA（质量）/ PERF（性能）等
- 例：`SAF-004 不碰雇主与客户信息`、`BUL-003 数字必须挂来源`

## 三、编写准则（一条合格规则的五个要求）

1. **可判定**：能不能被机器/清单检查？"要保证质量"不合格，"发布前跑 validator 门禁"合格
2. **单一职责**：一条规则只约束一件事，不要大杂烩
3. **可执行**：给出触发时机 + 具体动作（何时查 / 查什么 / 不过怎么办）
4. **简明**：每条 ≤ 3 行核心，长规则拆分子条
5. **留痕**：规则编号 + 版本 + 变更原因（可回滚）

## 四、通用规则示例（可直接借鉴）

### 宪法级
- **真实为本**：不虚构事实、不编造数据、不伪造引用；每个数字/引用必须有来源
- **不泄密**：密钥/凭据/内部数据绝不进入公开内容；发布前过敏感扫描
- **去 AI 味**：用人话写作，拒绝模板腔（"首先/其次/赋能/闭环"类禁词）

### 标准级
- **发布门禁**：发布前必须：敏感扫描通过 + README 与实际一致 + 无未完成占位
- **引用规范**：外部事实附来源 URL，区分"已查证"与"一方称"
- **交付检视**：宣称完成前回读产物、逐项验证，不把"应该"当"已经"

### 按需级
- 单项目专用：临时性局部约束（如某仓库的命名规范）

## 五、规则的生命周期

```
起草（编码 + 单条文件）→ 评审（过"可判定"五问）→ 发布（更新索引）→ 执行（agent 读取）
→ 复盘（误伤/失效？）→ 修订或归档
```
> 规则是活文档：定期清理失效规则，避免"规则通货膨胀"（太多等于没有）。

## 六、目录结构

```
rules/          # 通用规则（可跨项目复用）
rules-scoped/   # 作用域规则（按项目/场景）
SELF.md         # 本仓专业自述
```

# XRULE-001 Analysis｜SDD 进入分析

## 问题与机会

当前仓库自述把规则描述为分层、可检索资产，但部分文案把“文件存在/放入目录”与“运行时加载、模型遵守”混为一谈；README 声称统一 frontmatter，而现有 `rules/engineering-rules.md` 未显示相应 YAML 元数据。以上为基线检视发现，具体运行时行为尚未实测。

本任务要建立从规则资产描述到使用证据的可追溯契约，让用户和 Agent 能回答：规则为何存在、何时适用、依赖什么、目标平台支持什么、如何验证及如何回退。

## 用户与成功结果

目标用户为维护编码规范、架构约束和质量要求的工程师，以及将规则组合进不同 Coding Agent/Harness 的维护者。成功结果不是规则数量增加，而是公开文档不夸大平台能力、规则包能自描述、组合关系有来源、样例能用正反例检查。

## 事实、推论与提案

- **FACT**：仓库有 README、SELF、AGENTS 和 `rules/engineering-rules.md`；AGENTS 要求先写非平凡任务 Spec 并核对目标运行时机制。
- **FACT**：独立对抗审查发现范围膨胀、平台资料漂移、论文与产品证据混淆、脱敏不等于授权、Harness 关系缺实证、来源仓权属未知、验收偏主观等风险。
- **INFERENCE**：现有文档需把 Rule 资产与其适配/执行能力分开表达。
- **PROPOSAL**：采用 Rule Pack（规则、元数据、正反例、证据清单）与 Runtime Adapter（目标运行时的发现/加载/过滤/记录）两类对象；规则本身无需实现成运行时代码插件。
- **UNKNOWN**：各 Agent 当前具体版本和加载机制；Harness 当前依赖/安装行为；本地候选规则版权及可转授权状态。

## 目标与范围

以 `task-contract.md` 为范围/归属/闸门 SSOT。本 Spec 将结果拆阶段：事实与来源核验 → 架构与文档契约 → 样本准入及独立撰写 → 目标运行时验证 → 对抗审查和 Draft PR。

不会建设注册中心或通用运行时，不修改关联仓和本地源仓，不自动安装/发布/合并，不把提示词或 Markdown 说成权限控制。

## 关键风险与缓解

| 风险 | 缓解与失败处理 |
|---|---|
| 内部/客户材料误入公开仓 | 样本先权属准入；权属不明则不使用源材料，改为全新独立撰写；隐私扫描不通过即停止 |
| 平台版本或加载机制过时 | 只引用官方原始文档，记录版本与核验日期；无法实测标 `not-tested` |
| 研究启示被说成产品证明 | 每条研究记录写发现、推论、局限、所需本地验证 |
| 建议组合伪装成实装依赖 | 每条实装边附 manifest/脚本证据；建议边明确标注 |
| 计划范围过大 | 每个阶段独立闸门；G1/G3 不通过时不得跳至样本发布 |

## 备选方案

1. **只改文档**：成本低但无法证明规则可自描述或可验证；不推荐作为最终目标。
2. **先做大型适配器**：跨平台覆盖面大，但事实、契约和权属均未清楚，易过度建设；排除。
3. **分阶段规则资产 MVP**：先核实事实，再形成契约和一个可准入样本，最后实测一个平台；推荐。

## 验收思路

具体断言见 `task-contract.md`。至少满足：概念边界准确；官方兼容说法有来源/日期/限制/测试状态；研究论证不越界；关系图实装边可追溯；样例含正反例和适用/不适用边界；运行时验证有版本、安装/加载步骤和观察证据。未完成项明确为 NOT_RUN/UNKNOWN，不得用预期结果代替实测。

## 开放问题

1. XRULE 是否有权将本地候选规则的通用部分重新许可至 MIT？当前未知，需在 WP0/G3 核实。
2. 第一版实测目标平台选择 Claude Code 还是 DSH？需先核对可操作环境、官方机制及可留证方式。
3. 官方平台矩阵是否覆盖全部七个平台，或先仅覆盖当前有可复现测试条件的平台？由 WP0 事实和实施成本裁定，未测平台不宣称支持。
